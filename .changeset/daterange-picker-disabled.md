DateRangePicker's `disabled={true}` now disables the whole picker, as DatePicker's does. It disabled every day in the calendars but left all four triggers enabled, so the From and To triggers looked enabled, took Tab focus, were announced as operable buttons, and each opened a calendar in which nothing could be picked: below `lg:`, a dialog with no close button. Now every trigger the picker renders takes native `disabled` and the `default-outline` Button's disabled look, Tab skips it, and a click, Enter or Space opens nothing. A disabled trigger keeps its text, its accessible name and its description. Its `From:` / `To:` prefix, always `txt-black-500` before, now takes `txt-black-disabled` whenever the trigger it sits in is `:disabled`, so it dims inside a `<fieldset disabled>` as well, where only the date used to dim. An enabled picker in the first `<legend>` of a `<fieldset disabled className="group">` keeps a `txt-black-500` prefix. Any other `disabled`, such as `{ before: date }`, a function, an array of Matchers (`[true]` included) or `false`, still leaves the triggers enabled, and the calendars disable the same days as before. A `<fieldset disabled>` you wrapped around a DateRangePicker only to disable its triggers can go. `disabled` keeps its type, `Matcher | Matcher[]`, and its JSDoc on both pickers now says that `true` disables the whole picker and any other value only the days it matches. `full.css` in `@amerfathullah/myds-style` carries the new class.
