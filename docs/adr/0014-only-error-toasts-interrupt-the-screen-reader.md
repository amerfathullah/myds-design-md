# Only error toasts interrupt the screen reader

Every toast came from upstream announced assertively, whatever its Variant (#198). Radix announces each toast in its own visually hidden `role="status"` span, whose `aria-live` follows Root's `type`: `assertive` for `foreground`, Radix's default, and `polite` for `background`. Neither ToastRoot nor AutoToast set `type`, and `toast()` couldn't. So a `success` toast interrupted the screen reader just as an `error` did. Assistive technologies may also clear what they had queued when an assertive message arrives (ARIA 1.2, and Radix's docs), so of two toasts that AutoToast stacks, the second can silence the first, even when the first is an error. The design guideline doesn't say how a toast is announced, so this is a Gap. But its Variants differ in urgency. Error "Notifies the user of an error that requires resolution before proceeding", the only Variant that stops the user. Success "Indicates a successful action", and Information "Provides additional details to keep the user informed". WCAG 2.2's Understanding document for 4.1.3 gives `role="status"`, which is polite, to a message that "advises on the success or results of an action", and `role="alert"`, which is assertive, to "a warning on the existence of an error". It lists `aria-live="assertive"` on "content which is not important and time-sensitive" as a failure. ARIA 1.2 says authors SHOULD NOT use `assertive` unless the interruption is imperative. So ToastRoot sets `type` by Variant. `error` is `foreground`. `message`, `success`, `info` and `warning` are `background`, and so is a toast whose `variant` is unset or `null`, which is a `message`. The author can set `type` on any toast: on a hand-composed ToastRoot, on AutoToast for all its toasts, or through `toast()`, whose `ToastEvent` gains `type`. A toast's own `type` wins over AutoToast's, and AutoToast's wins over the Variant default. An author passes `type="foreground"` to a toast of another Variant that must be heard at once, and `type="background"` to an error that can wait.

## Why Toast differs from Callout and AlertDialog

ADR-0010 rejected choosing Callout's role by Variant, for two reasons. The guideline splits callouts by where they're used, not by Variant. And whether a `status` that mounts with its text already in it is announced is unverified. #303 rejects choosing AlertDialog's role for the first reason, and because the role changes "when an author changes only the colour". The first two reasons don't hold for Toast. The guideline gives a toast one context: it "appears after a user performs an action". So the Variant is the only signal left. And Radix's span mounts empty and fills two frames later, so ADR-0010's open question doesn't arise. #303's colour reason does hold: an author who changes only an error's colour to a warning's also makes it polite. This ADR accepts that. The role stays `status` for every Variant, only how urgently a toast is announced changes, and the guideline ties that urgency to the Variant: only Error "requires resolution before proceeding".

## Considered Options

- **`foreground` for every Variant**, as before, but set by MYDS instead of left to Radix: rejected. Radix's docs advise `foreground` for "toasts that are the result of a user action", and the guideline's toast appears after one. But Radix's rule is about where a toast comes from, not how urgent it is. Under it, "Disimpan" interrupts as urgently as an error that blocks the user. Every toast that AutoToast stacks would also be assertive, and Radix's docs themselves say to "avoid stacking distinct foreground toasts at the same time". Radix warns that overusing `background` after a user action "can be perceived as a laggy user experience for screen reader users". For a toast that isn't an error, this ADR accepts that delay over the interruption.
- **`background` for every Variant**, with `foreground` on request: rejected. It reads the guideline's "Non-intrusive notification" as being about how a toast is announced. But the same page says an error "requires resolution before proceeding". The error would wait for a pause in what the screen reader is saying. A user who presses a key first may never hear it, since Radix removes its announcement a second after it mounts. Only authors who remembered to pass `foreground` to every error would avoid that.
- **`warning` as `foreground` too**: rejected. Warning "Alerts the user to take notice", but the guideline says it's "often used for reminders or actions that require attention, such as reporting spam", which don't stop the user. Only Error does. An author passes `type="foreground"` to a warning that must be heard at once.
- **A new prop**, such as `urgent`, `announce` or `live`: rejected. ToastRoot and AutoToast already accept Radix's `type`, so a new prop would do what `type` does, as ADR-0010 said of an `announce` prop for Callout. `ToastEvent` takes the same name and values.
- **The default before `{...props}`**, where ADR-0008 puts built-in names and ADR-0010 puts Callout's role: rejected for `type`. AutoToast passes each toast's `type`, which is often `undefined`, and a `type={undefined}` spread after a default would reach Radix and become `foreground`. Unlike a role, `type` has no "none" for an author's `undefined` to choose: it could only mean Radix's `foreground`. So ToastRoot takes `type` out of its props with a default, as it already does for `variant` and `duration`, and a `type` left undefined gets the Variant default. An author's `type` still wins. Radix's own default is never reached.

## Consequences

- A `message`, `success`, `info` or `warning` toast is announced at the next pause, such as the end of the sentence the screen reader is reading, and it doesn't clear what was queued. Toasts that arrive together are queued, not cut off, though an error among them can still clear the others. Two errors at once can still interrupt each other, so the docs say to avoid showing them together.
- An error toast still interrupts. Like every toast, it still closes after its `duration`. Whether an error that "requires resolution before proceeding" should stay until it's dismissed is a separate question (#392).
- `type` sets how urgently a toast is announced. It isn't the design guideline's Type, which is `variant` (CONTEXT.md). The docs (EN, MS), DESIGN.md and the JSDoc say so wherever they name it. The develop pages link to Radix's reference for ToastRoot's other props, so they also say that MYDS's default differs from Radix's.
- The order, highest first: a toast's own `type` (in `toast()` or on a hand-composed ToastRoot), then AutoToast's `type`, then the Variant default. In AutoToast, `type` is the only field where a toast's own value wins: AutoToast spreads its other props after each toast's `variant`, so they apply to every toast. A comment in the code says why.
- Nobody has tested this with a screen reader. Radix removes its span a second after it mounts. Whether a polite announcement still queued at that moment is read is unverified. If it isn't, a toast that isn't an error can go unheard while the screen reader is speaking, and its author can pass `type="foreground"`.
- DESIGN.md's Toast entry says how each Variant is announced, and Known Gaps records the Gap. The Gap stays after the change, as TimeField's and Skeleton's do, because the guideline still doesn't say.
- The docs site's own toasts follow the Variant default, because its AutoToast passes no `type`: its Error example still interrupts, and the rest become polite.
- The change ships as a minor release of `@amerfathullah/myds-react`, in the same release as ADR-0010's, which is a minor too. `ToastEvent` gains a field, and what users hear changes for four of the five Variants. The changeset says that only error toasts interrupt now. It tells authors how to bring back the old behaviour: `<AutoToast type="foreground" />` for every toast, `type: "foreground"` in `toast()` for one, or `type="foreground"` on a hand-composed ToastRoot. It also tells them to update tests that expect `aria-live="assertive"` on a toast that isn't an error.
