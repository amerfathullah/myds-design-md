# Only error toasts interrupt the screen reader

Every toast came from upstream announced assertively, whatever its Variant (#198). Radix announces a toast in a visually hidden `role="status"` span whose `aria-live` follows Root's `type`: `assertive` for `foreground`, Radix's default, and `polite` for `background`. Neither ToastRoot nor AutoToast set `type`, and `toast()` couldn't. So a `success` toast interrupted the screen reader just as an `error` did. Assistive technologies may also clear what they had queued when an assertive message arrives, so of two toasts that AutoToast stacks, the second can silence the first, even when the first is an error. The design guideline doesn't say how a toast is announced, so this is a Gap. But its Types differ in urgency. Error "requires resolution before proceeding", the only Type that stops the user. Success "indicates a successful action", and Information "keeps the user informed". WCAG 2.2's Understanding document for 4.1.3 treats the result of an action as a status, which is polite. ARIA 1.2 says authors SHOULD NOT use `assertive` unless the interruption is imperative. So ToastRoot sets `type` by Variant. `error` is `foreground`. `message`, `success`, `info` and `warning` are `background`, and so is a toast that leaves `variant` out, which is a `message`. The author can set `type` on any toast: on a hand-composed ToastRoot, on AutoToast for all its toasts, or through `toast()`, whose `ToastEvent` gains `type`. A toast's own `type` wins over AutoToast's, and AutoToast's wins over the Variant default. An author passes `type="foreground"` to a toast of another Variant that must be heard at once, and `type="background"` to an error that can wait.

ADR-0010 rejected choosing Callout's role by Variant, and #303 rejects choosing AlertDialog's, for three reasons. Their guidelines split them by where they're used, not by Variant. A role that follows the Variant changes "when an author changes only the colour" (#303). And whether a `status` that mounts with its text already in it is announced is unverified. None of these holds for Toast. The guideline gives a toast one context: it "appears after a user performs an action". So the Variant is the only signal left. Every toast is announced through the same `status` span, and only how urgently changes. The span mounts empty and fills two frames later, so either urgency is announced. And a toast's Variant is more than its colour: under ADR-0013 the title names the Variant, so an author who changes an error to a warning changes what the toast says.

## Considered Options

- **`foreground` for every Variant**, as before, but set by MYDS instead of left to Radix: rejected. Radix's docs advise `foreground` for "toasts that are the result of a user action", and the guideline's toast appears after one. But Radix's rule is about where a toast comes from, not how urgent it is. Under it, "Disimpan" interrupts as urgently as an error that blocks the user. Every toast that AutoToast stacks would also be assertive, and Radix's docs themselves say to "avoid stacking distinct foreground toasts at the same time". Radix warns that `background` after a user action "can be perceived as a laggy user experience for screen reader users". For a toast that isn't an error, this ADR accepts that delay over the interruption.
- **`background` for every Variant**, with `foreground` on request: rejected. It reads the guideline's "Non-intrusive notification" as being about how a toast is announced. But the same page says an error "requires resolution before proceeding". The error would wait behind whatever the screen reader is saying, and a user who presses a key first may never hear it before it closes, unless every author remembered to pass `foreground` to every error.
- **`warning` as `foreground` too**: rejected. Warning "Alerts the user to take notice", but the guideline's uses for it are reminders and "actions that require attention, such as reporting spam", which don't stop the user. Only Error does. An author passes `type="foreground"` to a warning that must be heard at once.
- **A new prop**, such as `urgent`, `announce` or `live`: rejected. ToastRoot and AutoToast already accept Radix's `type`, so a new prop would do what `type` does, as ADR-0010 said of an `announce` prop for Callout. `ToastEvent` takes the same name and values.
- **The default before `{...props}`**, where ADR-0008 puts built-in names and ADR-0010 puts Callout's role: rejected for `type`. AutoToast passes each toast's `type`, which is often `undefined`, and a `type={undefined}` spread after a default would reach Radix and become `foreground`. So ToastRoot destructures `type` as it already destructures `variant` and `duration`, and a `type` left undefined gets the Variant default. An author's `type` still wins. Radix's own default is never reached.

## Consequences

- A `message`, `success`, `info` or `warning` toast waits until the screen reader has finished what it's saying, and it doesn't clear what was queued. Toasts that arrive together are read in turn. Two errors at once can still interrupt each other, so the docs say to avoid showing them together.
- An error toast still interrupts. Like every toast, it still closes after its `duration`. Whether an error that "requires resolution before proceeding" should stay until it's dismissed is a separate question (#ISSUE_AUTODISMISS).
- `type` sets how urgently a toast is announced. It isn't the design guideline's Type, which is `variant` (CONTEXT.md). The docs (EN, MS), DESIGN.md and the JSDoc say so wherever they name it. The develop pages link to Radix's reference for ToastRoot's other props, so they also say that MYDS's default differs from Radix's.
- The order, highest first: a toast's own `type` (in `toast()` or on a hand-composed ToastRoot), then AutoToast's `type`, then the Variant default. In AutoToast this is the opposite of `variant`, where AutoToast's own props win over each toast's. A comment in the code says why.
- Nobody has tested this with a screen reader. Radix removes its span a second after it fills. Whether a polite announcement still queued at that moment is read is unverified. If it isn't, a toast that isn't an error can go unheard while the screen reader is speaking, and its author can pass `type="foreground"`.
- DESIGN.md's Toast entry says how each Variant is announced, and Known Gaps records the Gap. The Gap stays after the change, as TimeField's and Skeleton's do, because the guideline still doesn't say.
- The docs site's own toasts become polite, because its AutoToast passes no `type`.
- The change ships as a minor release of `@amerfathullah/myds-react`, as ADR-0010's did: `ToastEvent` gains a field, and what users hear changes for four of the five Variants. The changeset says that only error toasts interrupt now. It tells authors that `<AutoToast type="foreground" />` brings back the old behaviour for every toast, and `type: "foreground"` in `toast()` for one. It also tells them to update tests that expect `aria-live="assertive"` on a toast that isn't an error.
